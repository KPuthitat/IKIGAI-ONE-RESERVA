# CLAUDE.md — Project guardrails

Read this file at session start. The rules below are operational lessons
learned from real incidents on this codebase — follow them.

## Before suggesting a deploy

The owner deploys directly to prod (no staging). Staff use the system
during business hours, so a bad deploy at the wrong moment locks
people out mid clock-in.

**ALWAYS check the deploy window before saying "deploy now":**

```bash
curl -s http://ikigaimedihealth.com/api/deploy-window
```

Reads roster + shift_codes for today across all branches. Returns:

```json
{
  "safe": true | false,
  "warnings": ["NAMA · NPF เข้างาน 08:00 (อีก 7 นาที)"],
  "nextSafeAt": "2026-05-28T08:31:00.000Z"
}
```

- `safe: true` → green light, suggest deploy
- `safe: false` → DO NOT silently suggest deploy. Surface the warnings to
  the owner verbatim and ask them to decide. Mention `nextSafeAt` if it's
  within an hour.

**The safe window (owner 2026-06-12):** deploy ONLY when now is outside a
±30-minute band around EVERY branch's clock-in and clock-out times. I.e.
no branch has anyone entering/leaving within the next or last 30 minutes.
The `/api/deploy-window` API encodes this rule — trust its `safe` flag, but
this is the definition behind it. When it's clear, you may proceed without
asking again.

deploy.sh runs the same check and prompts y/n; the API is for you so
you can warn BEFORE the owner runs the script.

## Before pushing schema changes

The migration regex bug on 2026-05-28 cost the owner the morning
clock-in window. To prevent a repeat:

- **ALWAYS run `npx tsc --noEmit -p tsconfig.json` locally before
  pushing any commit that touches `src/lib/db.ts` or any migration
  path.** Exit 0 is required.
- For schema rebuilds (CHECK widening etc.), prefer explicit
  alternations over `\b`-anchored regex — backtracking on quoted
  identifiers like `"users"` produces invalid SQL silently.
- After push, **wait for GitHub Actions CI to go green** before
  telling the owner to deploy. CI runs the same `tsc --noEmit`.

## Maintenance during deploy

Two layers protect users mid-deploy:

1. **In-page banner** (`MaintenanceBanner.tsx`) — owner toggles ON
   before deploy → renders sticky blue strip on every page. Useful as
   a heads-up.
2. **Nginx maintenance page** (`/var/www/maintenance/index.html`,
   generated by `lib/maintenance-page.ts`) — served automatically by
   Nginx via `error_page 502 503 504` when Next.js is unreachable.
   Self-contained HTML with embedded owl + LINE Seed Sans TH font.

The banner is for WARNING, the Nginx page is for WHILE-IT'S-DOWN. They
share the same `system_settings.maintenance_message`.

## Common pitfalls

- **`status != 'disabled'`** — also exclude `'resigned'`. Use
  `status NOT IN ('disabled', 'resigned')` instead.
- **`role = 'staff'`** — admins are employees too. Use
  `role IN ('staff', 'admin')` for HR operations (leave, payroll,
  resignation, reports, etc.).
- **SQLite NULL ≠ NULL in UNIQUE** — for nullable-scope columns
  (e.g. company-scope ASCENDA results), do a lookup-first dedup
  instead of relying on UNIQUE.
- **Better-sqlite3 native binding** — Node 24 has no prebuilt for
  better-sqlite3 11.x yet. Local dev should use Node 22 LTS.

## Workflow

```
1. Plan with the owner (use AskUserQuestion liberally)
2. Code locally — touch as few files as the task requires
3. Review + test BEFORE moving on (owner standard 2026-06-12 — a large
   system gets unmanageable if problems pile up):
     - self-review the diff (run /code-review) and fix what it finds
     - npx tsc --noEmit -p tsconfig.json   ← mandatory
     - run relevant tests (npm run test:rbac / test:mounjaro) +
       npm run check:i18n + npm run check:risks
   Never carry unverified code into the next task.
4. ALWAYS commit + push to GitHub — git push origin main (owner standard
   2026-06-12: don't leave finished work only on the local machine)
5. Wait for GitHub Actions CI to go green (40s)
6. curl /api/deploy-window before suggesting deploy (see ±30-min rule above)
7. Owner SSHs in, runs /var/www/reserva/scripts/deploy.sh
8. Owner reports back; if anything broke, debug from pm2 logs
```

## When work is deploy-ready — hand it over WITHOUT being asked

Owner standard 2026-07-13 ("อย่าให้ต้องบอกทุกครั้ง"): every time a change is
finished and pushed (CI green), proactively send BOTH of these — don't wait
for the owner to ask:

1. **A ready-to-copy handoff** — the deploy command (`ikigaios-deploy`), a
   one-line summary of what's in this batch, the commit hash, and whether it
   carries a migration (touches `src/lib/db.ts`). Format it so the owner can
   copy-paste and go.
2. **A post-deploy test checklist** — checkbox items grouped by feature/phase:
   which page to open, what to click, and what the correct result looks like.
   Cover every user-facing change in the batch.
